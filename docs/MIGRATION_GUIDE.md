# 設計書を Markdown に移行する進め方（ロット運用）

Excel・Word・PowerPoint の設計書を、AI が読める Markdown + draw.io の図に移すときの進め方です。
一度に全部を移さず、**文書の種類ごとに小さなロットで** 移し、原本との突合を機械と人の両方で行います。

## 1. 方針

| 項目 | 決めておくこと | 推奨 |
|---|---|---|
| 正本 | 移行中、どちらを正とするか | 移行が完了してレビューを通るまでは Office の原本が正。通った文書から Markdown を正にする |
| 並行管理 | 原本の更新をどう反映するか | 移行中の原本更新は禁止期間を設ける。やむを得ず更新したら再変換（`source_sha256` で検知） |
| 順番 | どの種類から移すか | 表・文章が中心の文書（API 定義・バッチ定義）→ 図が中心の文書（業務フロー・構成図）の順 |
| ID | 文書の識別子 | Front Matter の `id`（例 `DOC-API-0001`）。ファイル名に頼らない |

## 2. 1 ロットの流れ

```mermaid
flowchart LR
  A["対象を決める<br/>同じ種類 10〜20 文書"] --> B["dry-run<br/>読み方・不足ソフト確認"] --> C["変換<br/>--front-matter --llms-txt"]
  C --> D["機械チェック<br/>loss.* の警告を確認"] --> E["図の作り直し<br/>figspec / draw.io"] --> F["人の突合<br/>チェックリスト"] --> G["レビュー・承認<br/>Markdown を正に"]
```

```bash
doc2md 設計書/API/ --dry-run -r                          # 1) 処理方法と必要なソフトの確認
doc2md 設計書/API/ -d md/api -r --front-matter --llms-txt -f json -o report.json   # 2) 変換
```

3. `report.json` の `loss.*`（変換で欠けた可能性）を全件確認する。欠けている箇所は `--via-pdf` で再変換して見比べる
4. 図は、変換結果の「要素」「接続」を見ながら figspec（YAML）で作り直すか、draw.io で直接直す（画像のままにしない）
5. 人の突合（下のチェックリスト）をして、レビューで承認する
6. Front Matter の `id` を付け、Markdown を正本にする。原本は「参照用・更新禁止」として保管する

## 3. 人の突合チェックリスト

- [ ] 見出しの数と順番が原本と同じ
- [ ] 表の行数・列数が原本と同じ。結合セル・2 段見出しの意味が崩れていない
- [ ] 注記（※）・欄外の補足・コメント・変更履歴が残っている（必要なら）
- [ ] 図の要素と接続（矢印の向き・ラベル）が原本と同じ
- [ ] 画像の文字（スクリーンショット等）を本文にした場合、誤字が無い
- [ ] 数値・日付・コード値が原本と一致（抜き取りで 10 箇所）
- [ ] AI に必要な情報（パラメータファイル名・メッセージ ID・テーブル名）が明記されている

## 4. 変換のコツ

| 状況 | 対処 |
|---|---|
| Excel の見出し行が自動検出と違う | `--header-row "シート名=4"` |
| 数式の結果が空 | `--recalc`（LibreOffice で再計算） |
| 非表示の行・列が混ざる | `--skip-hidden` |
| レイアウトが崩れる | `--via-pdf` で PDF 経由と見比べる |
| スキャンした PDF | `--ocr-lang jpn`（Tesseract と日本語データが必要） |
| 変更履歴を残したい | `--track-changes show` |
